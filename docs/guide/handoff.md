# Session handoff

Three small files (STATUS.md, tasks.json, PROGRESS.md) so a new session picks up where the last one stopped.

[← README](../../README.md) · [Türkçe](../rehber/handoff.md)

**Keeping it current.** The files only help if they are written. In a project that has them, crew-chief counts what happens and reminds Claude (it never writes them itself, never asks you a question, never stops a call): after `handoff.files` distinct project files were edited (generated files, `node_modules`, lock files and other folders do not count; subagent edits do) or a third of that many over `handoff.minutes`; the reminder rides with the result of an Edit/Write call, so it reaches a long unattended run too, and with your next prompt. Separate one-time reminders: your message may state a lasting rule (copy it word for word into Constraints), you answered one of Claude's questions (a decision), a commit was made (update the task's status and evidence), or a usage limit is nearly used (a limit stop ends the session without warning). Any write to the files, even from a shell, restarts the count; reminders are spaced out, get louder once, and stop after three unanswered ones. Not while a compaction is under way (that flow updates them itself). With `handoff.mode turn`, if reminders went unanswered and the pile is twice the trigger, one extra turn at the end of an answer asks for the update, once per stretch, only when nothing else is running. A hint, not a guarantee: an abrupt end between two reminders can still leave the files behind.

A new session starts with no memory of the last one, so it rediscovers the project: what works, what was tried, what is next. Crew Chief can set up three small files that carry that over. This follows Anthropic's engineering post [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) (Nov 2025): a progress file, a JSON task list whose status is the only thing that changes (models are less likely to rewrite JSON than Markdown), and reading `git log` plus the progress file at the start of each session.

| File | Holds | Changes how |
|---|---|---|
| `STATUS.md` | Now, environment commands, next, open questions, failed attempts, decisions | Rewritten to describe the present |
| `tasks.json` | Tasks with `id`, `title`, `priority`, measurable `done_when`, `status`, `evidence` | Only `status` and `evidence` change: `todo` → `in_progress` → `done` (every part of `done_when`, sign-offs included) or `blocked` (reason in `evidence`) |
| `PROGRESS.md` | Dated log, newest first | One paragraph appended per session |
| `CLAUDE.md` | A start/end routine between `<!-- crew-chief:handoff:start -->` and `:end` markers | Added once; the rest of the file is not touched |

**Asked as a question when the mod is loaded.** On a fresh startup (a person at the prompt, no prompt sent yet: not resume, fork or `/clear`) the mod asks *Set up / Later / Never* itself, and in a folder with no git repository (a real project folder: not your home directory, a temp folder or an empty one) *git init, then set up / Set up without git / Later / Never*. Unanswered, the question takes *Later* after the question deadline. *Later* and *Never* write the same lines to `handoff-offers.tsv` as below, and the same quiet rules apply. *Set up* runs the `crew-handoff` skill, which already knows you said yes: it shows the plan and preview and writes the files in the same turn (it waits only when equivalent files already exist). While the mod is loaded it leaves `mod-offer-active` (a unix time) in the plugin's data folder and the session hook's text line below stays quiet for 14 days after it; without the mod the text line is the offer.

**Weekly consistency check.** At a fresh startup in a project that has `STATUS.md` or `tasks.json`, at most once per 7 days per project (recorded in `handoff-checks.tsv`, written by the hook), the hook asks Claude to compare `STATUS.md` *Now*/*Next* with `git log` and the `tasks.json` statuses while it reads them anyway, and to report in at most three lines at the end of its first answer. It also mentions a `STATUS.md` over 6 KB, a `CLAUDE.md` over 200 lines, `PROGRESS.md` entries older than 60 days and a `tasks.json` over 60 KB (`/crew-tidy` gives the detail, `/crew-tidy archive` moves old progress). Advisory only; never on resume, `/clear` or compaction.

**How it is offered.** On a fresh session start (not resume, `/clear`, or compaction) in a git repository that has none of these files yet, the session hook asks Claude to do your request first and then add one short line at the end of its answer offering the files (never a dialog; skipped for overnight, background or looped jobs and non-interactive runs). Showing it counts as *later* (offered again after 7 days); say yes to set them up, or "never" for this project. The hook stays quiet:
- when any handoff-like file already exists at the root or one level down, under common names (`tasks.json`, `STATUS.md`, `PROGRESS.md`, `HANDOFF.md`, `claude-progress.txt`, `feature_list.json`, and their Turkish equivalents `durum.md`, `ilerleme.md`) or as a `crew-chief:handoff` block in `CLAUDE.md`;
- outside git repositories, in your home directory, and in temporary directories;
- when `CREW_CHIEF_HANDOFF_OFFER=off` is set in your environment.

**What setup does** (`/crew-chief:crew-handoff`, or just say "set up handoff files"): it looks for existing equivalents first and offers to keep using them instead of creating a parallel set; shows the files and a preview filled only from what it can verify in the repository (unverifiable items are marked unverified); creates only missing files; adds the `CLAUDE.md` block; never overwrites, renames, or commits anything. `/crew-chief:crew-setup --handoff` runs the same steps after a project install.
